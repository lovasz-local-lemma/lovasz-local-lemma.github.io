The idea behind it

I started with Fortune and Apollonius visualizers, then wanted to see the decisions behind the construction as closely as the geometry itself. Difficult inputs make that especially revealing: the event structure and arithmetic can determine whether a plausible picture is actually the right one.

Working intuition Geometric correctness depends on the events and arithmetic that produce the picture.

Deliberate scope The detailed workbench prioritizes geometric decisions, precision and difficult cases over a minimal interface. A lighter presentation is a separate design goal; hiding the numerical machinery here would remove much of what I wanted to inspect.

01 · Motivation

A diagram is only the visible result

A Voronoi diagram assigns each position to its nearest site. That definition fits in one sentence, and a final picture can look uncomplicated. Implementing Fortune's sweep requires a different level of detail: locating a changing arc, splitting it without losing its neighbors, invalidating predictions made from an earlier neighborhood, and preserving the meaning of a breakpoint while the tree beneath it rotates. These operations are the substance of this project.

I usually try to make an algorithm understandable with as little visual machinery as possible. Fortune’s Loom takes a deliberately denser route: the main viewport stays direct and interactive, while the beachline, event queue, tree mutations and numerical decisions remain visible beside it. The beauty is in seeing these parts agree as the construction unfolds.

The workbench presents geometry and implementation state together. A circle event can be followed from its defining sites to its queue entry, disappearing arc, tree mutation and emerging vertex. A tree is useful here because it explains an actual operation; the animation is useful because it identifies when that operation occurred. The result is a visual systems study of a difficult geometric algorithm, with the final tessellation as one of several outputs.

The original Crystal implementation and the C++ trees/beachline infrastructure were written without AI assistance. The Crystal recordings remain part of the project's history. The current C++ edition adds a common execution interface, multiple structural policies and explicit diagnostic comparisons; the older prototype's presentation does not establish the current engine's correctness.

The whole algorithm on stage

The extra panels are deliberate. Follow one event from its geometric cause to the queue, the changing tree and the numerical comparison: the interface is heavy because the relationships are the subject.

02 · Sweep construction

The frontier turns geometry into events

For a site above a horizontal directrix, the points equally distant from the site and the directrix form a parabola. The beachline is assembled from the relevant portions of these parabolas. As the directrix descends, neighboring arc intersections move along Voronoi bisectors. The continuous picture therefore has a discrete structure: the active neighborhood changes at site arrivals and arc collapses.

The parabolas are temporary construction geometry. They are not the final Voronoi edges, and a moving breakpoint is not a new input point. Showing these roles simultaneously helps separate the input sites, the frontier, the prediction of a future event and the persistent edge trace. The original visualizer already emphasized this distinction through highlights linking an arc to its structural representation.

Fortune's classical event-driven formulation supplies the familiar O(n log n) algorithmic motivation when efficient search and event operations are maintained. The instrumented workbench records complete snapshots and performs additional checks, so its end-to-end recording cost is a different measurement. Smooth playback demonstrates inspectability; it is not an uninstrumented sweep benchmark.

03 · Geometry meets data structure

An insertion is more than adding a tree node

A general site arrival splits an existing arc and inserts the new site's arc between the surviving pieces. The same site may consequently appear in more than one beachline arc. Site identity and arc identity have different jobs: a site identifies geometric input, while an arc identifies one active piece of the frontier. Treating them as interchangeable makes deletion and event invalidation particularly fragile.

The implementation maintains a search structure together with explicit predecessor and successor links. The tree locates the arc above a new site; the threaded neighbors identify the local triples that can create circle events. A rotation changes the search structure while preserving the intended left-to-right order. A split or removal changes that order and must update both representations coherently.

Equal-height input is a useful stress case because the first row of parabolas is degenerate at arrival. The dedicated insertion rule places adjacent arcs instead of applying the ordinary formula at its singularity. The regression suite checks this first-row order across all six backends, making the exceptional path part of the tested implementation rather than an incidental feature of the drawing.

The invariant worth watching

The in-order tree traversal and the threaded arc list must describe the same active sequence. The visual links make that agreement inspectable even when the tree's shape changes substantially.

04 · Event lifetime

A future event can stop being true

Three neighboring arcs can predict a collapse at the bottom of a circumcircle. That prediction depends on their adjacency. Before the directrix reaches it, another event may split an arc or change its neighbors. A stored circle and event coordinate remain numerically plausible even though the corresponding removal is no longer valid.

The current engines re-evaluate a queued collapse against the current neighboring triple before removing an arc. The interface distinguishes pending, current and invalidated events so that a discarded prediction has a visible explanation. This is a general event-system issue expressed in geometry: queue order alone cannot establish that an event's prerequisites still hold.

Cocircular sites add another difficulty. Several consecutive arcs may collapse at a shared vertex, making a sequence of ordinary single-arc removals sensitive to tiny numerical differences. Grouped collapse handles the contiguous run together and opens the replacement edge from the common event. The ring and grid examples make this behavior visible because several geometric relationships become simultaneous.

05 · Structural comparison

Two representations, six tree backends

The leaf-oriented representation stores arcs at leaves and breakpoints at internal nodes. The alternative places an arc at every node and derives breakpoints from neighboring arcs. Both represent the same geometric frontier, but their insertion, removal and bookkeeping requirements differ. Keeping both behind FortuneRunner makes the representation itself a subject of comparison.

The five arc-node policies are actual implementations with their own rotations and fix-ups. Switching from AVL to red-black or splay changes the maintained structure and recorded mutations, rather than merely rearranging a fixed picture. The shared threaded order provides a useful point of comparison when the tree shapes diverge.

Backend agreement supplies differential evidence, not an automatic oracle. The dedicated degeneracy regression checks structural snapshots for the arc backends and compares raw edge counts with the leaf implementation on square, ring and grid fixtures. Equal counts can still conceal different endpoints. The views and tests therefore distinguish structural checks from geometric output comparison.

06 · Failure and repair

Robustness is a set of concrete mechanisms

The robustness tests connect each known failure to a specific fix. This workbench retains historical changes so that a clean diagram can be related to particular implementation decisions. Grouped collapse and half-open edge direction disambiguation have regression examples where disabling the change reproduces a mismatch with the reference construction.

Queue ordering poses a separate problem. Epsilon-based equality can make a comparator non-transitive, violating the assumptions of an ordered container. The current event order is lexicographic over the represented keys: descending height, site before circle at a tie, ascending x and event identifier. It orders the computed values consistently without pretending those values are exact geometric event times.

Event storage is a lifetime problem rather than a precision problem. Nested insertion into a vector can invalidate a reference to an event currently being processed. The stable deque path addresses that failure. The historical vector experiment deliberately exposes undefined behavior and does not support a portable, repeatable wrong-result count. Separating these causes prevents numerical terminology from obscuring an ordinary memory-lifetime bug.

07 · Predicate provenance

Retain the formula; state the numerical limit

Small rounding differences can change an orientation sign, an event order or a vertex construction. The side-by-side modes make those consequences visible. Analytic Double evaluates with ordinary double precision; Low Precision first quantizes site coordinates; the mode labelled Lazy Exact preserves formulas and refines selected close comparisons. Some test configurations recover under the latter policy after the coarse mode fails, but the name does not establish a general exactness guarantee.

Lazy Exact is available in the browser. LazyScalar retains an expression DAG, while the predicate layer uses tolerance bands, numerical evaluation and a tie policy. The supported MSVC target gives long double the same significand precision as double; the checked Emscripten target reports 53 and 113 bits respectively and passes a wider-addition runtime check. Formula retention, extra precision and certified exact geometry are different properties. More bits cannot repair a construction that already lost information or supply a missing policy for simultaneous events.

Low-precision mode rounds working site coordinates to a decimal grid. It is an input-quantization experiment that can bring degeneracies into view. It does not model every operation of a lower-precision processor. This distinction makes the control more informative: a changed diagram can be related to a changed input rather than an unspecified numerical implementation.

Known cocircular boundary

The regular 12-site circle places a site exactly at the sweep's lowest point, so its site event is mathematically simultaneous with several cocircular collapses. Native and WebAssembly runs can leave a missing or misplaced raw-sweep spoke even with lazy_exact selected: the mode refines selected signs and retains formulas, but it does not provide exact constructions, symbolic event ordering or Simulation of Simplicity. Target arithmetic can change how the failure appears; WebAssembly is not itself the underlying cause.

08 · The second central study

Apollonius changes the geometry and the topology

Replacing a point's distance with distance minus a site radius changes more than the appearance of the cells. Equal-radius pairs retain line bisectors, while unequal-radius pairs can produce hyperbola branches. Some sites become dominated and contribute no cell. Curved boundaries, hidden sites and multiple candidate vertices make weighted geometry a substantive extension of the sweep investigation.

The current Apollonius implementation evaluates analytic pair curves and triple-vertex candidates, then filters pair visibility against competing sites. It assembles the retained polylines into a bounded half-edge structure with twins, face cycles and viewport stitching. The insertion playback exposes nearest-site search, hidden tests, conflict discovery and repair. The retained analytic state supports real reuse, while the current topology is assembled globally after insertion.

The additive metric is also available as a direct winner overlay. This layer colors sampled positions from their metric values and can look clean even when a thin DCEL gap remains. The validation grid compares those direct winners with cell ownership and distinguishes disagreements, gaps and overlaps. Sampling density controls how much of the plane is tested; an empty discrepancy view is a finite check rather than a proof everywhere.

09 · Apollonius · algorithm and implementation boundary

From the paper's predicates to a visual implementation

Description · at a glance

The bundled reference is Emiris and Karavelas, The predicates of the Apollonius diagram: algorithmic analysis and implementation. It analyzes the geometric decisions needed by the dynamic construction of Karavelas and Yvinec, including difficult degeneracies. The workbench follows that insertion narrative, then makes a different engineering choice: construct and inspect analytic candidate geometry, sampled visible curves and a bounded DCEL.

This is a working partial construction on the demonstrated and tested inputs. Its difference from the complete reference is more than speed: local topology repair, exact predicate fallback and the treatment of thin or degenerate features are not equivalent. Those distinctions identify the next implementation steps without obscuring what the current system already exposes.

ExplanationA quick tour of the reference algorithmLocate → reject hidden sites → classify conflicts → repair the graph.＋

The combinatorial construction is Karavelas and Yvinec's Dynamic additively weighted Voronoi diagrams in 2D (2002). It represents the diagram through its dual graph and supports both insertion and deletion. The bundled predicates paper develops the numerical decisions that make that graph construction robust; these are related contributions with different roles.

Insertion begins by locating the new site's nearest neighbor in the existing diagram. A containment test can then reject a site with no cell. Otherwise, the algorithm finds an initial conflict on the neighboring boundary and follows connected conflicts through the diagram's skeleton before repairing the affected graph.

The hard part is classifying a whole edge's conflict, not merely checking its endpoints. A new disk can remove an interior interval while leaving both ends, or affect the ends while an interior interval survives. Finite and infinite edge predicates distinguish these cases. The reference develops exact decisions using algebraic predicates, inversion and infinitesimal perturbation; the latter resolves degeneracies consistently.

Checking every stored point of a sampled curve is not a proof about the continuous curve between those points. The affected-pair shortcut can forward cached geometry after finding no sampled conflict; a sufficiently narrow newly occluded interval can escape that test. Increasing trace resolution can improve a particular case, but does not turn the test into an exact edge-conflict predicate.

A named thin-lens regression makes the topology issue concrete. Without the targeted repair, one triple-point tip has degree four and its partner degree two, producing extra outside-face cycles. The repair reassigns a branch and restores that fixture's expected topology. It is a bounded repair with before/after evidence, not a general replacement for robust analytic topology.

The random native invariant canary checks cell counts, connectivity and outside-face anomalies, but its failure mode currently logs warnings instead of failing the whole suite. Read these reports alongside the harder preset and repair assertions. Agreement with a rebuild using the same approximations is useful regression evidence, but it is not an independent exact oracle.

10 · 3D Fortune · conceptual exploration

From an ordered beachline to a beach surface

Description · at a glance

The 2D sweep works with a left-to-right sequence of parabolic arcs. Move the question into three dimensions and the sweep line becomes a plane: each active site contributes a paraboloid, and their lower envelope forms a beach surface. The concept mode displays that surface beside a top-down map of its competing patches.

The comparison explains why another coordinate is a structural change. A 2D arc has immediate neighbors in a sequence; a surface patch can border several other patches. Its adjacency becomes a graph that changes as the plane descends. The demo exposes those neighbors, highlights the newest paraboloid, records approximate patch births and disappearances, and accumulates traces near triple junctions.

This is an incomplete geometric illustration, available in both native and browser editions. It evaluates a sampled surface rather than maintaining a complete 3D Voronoi event algorithm. The useful result is seeing which part of the elegant 2D mechanism generalizes and which part needs a different data structure.

  • Pause the sweep and move the plane manually to compare one site's paraboloid with the current lower envelope.
  • Enable adjacency to compare the 2D chain of arcs with the 3D patch-neighbor graph.
  • Toggle the newest paraboloid, event markers and traced junctions to distinguish construction geometry from accumulated approximations.
Theory / mathematicsThe geometry that does generalizeEqual distance to a site and the sweep plane produces a paraboloid.＋

For an active site s=(sₓ,sᵧ,s_z) above the plane z=ℓ, equating the Euclidean distance to s with the distance to the plane gives the height below. Taking the minimum over active sites produces the envelope used by the illustration.

Boundaries between two surface patches lie on pairwise bisector sheets. Triple junctions are related to the one-dimensional Voronoi edge skeleton; generic 3D Voronoi vertices require four equidistant sites. The current traces are samples near triple junctions, not a certified list of those edges or vertices.

Theory / mathematicsA missing linear beachline order does not make events unsortableThe 2D data-structure recipe stops transferring directly; a priority queue remains possible.＋

A priority queue can still order predicted 3D events by sweep-plane height. Losing a left-to-right order among surface patches does not prove that event times cannot be sorted, or that every higher-dimensional sweep is impossible. The difficulty is predicting the relevant changes and updating a two-dimensional arrangement with a variable neighborhood.

The concept therefore motivates a boundary in this implementation rather than an impossibility theorem. An exact event engine would need explicit surface topology, robust event predicates and updates, and validation beyond the sampled patch map. The present demo intentionally leaves that machinery unimplemented.

11 · Comparative studies

Related constructions explain what changed

Delaunay, power, multiplicatively weighted and higher-order Voronoi studies provide comparison points for the central geometry. Their value is the change in question: adjacency can be examined through a dual construction; weights can alter the metric in different ways; a nearest-site decision can become a nearest-subset decision. These are distinct mathematical objects rather than interchangeable visual styles.

The Delaunay study relates site connections to Voronoi adjacency and circumcircle constructions. Degenerate configurations are particularly informative because a simple one-triangle/one-vertex picture requires care when several sites are cocircular. Weighted studies likewise distinguish curved additive-distance boundaries from the linear boundaries available to power-distance constructions.

These geometric relatives form a focused branch around the original construction. The separate Geometry + studies entrance opens the framework's broader collection: transforms, graphs, optimization and algorithm experiments. The Crystal AVL and red-black pages isolate ordinary tree operations from the moving geometric frontier.

12 · Recorded execution

The intermediate state is the explanation

A MutationObserver records the real insertions, removals and rotations. Snapshots retain node identities and links, neighboring arcs, breakpoints, edge traces, event queues and validation messages. Playback can connect a visual change to its originating mutation because those views share the recorded state.

The formula-preserving mode adds another level of inspection. Constructed values retain expression graphs with named input atoms, arithmetic operations and square roots. Comparison-forcing counts identify when a symbolic construction needed numerical evaluation. This makes a difficult coordinate or comparison traceable instead of reducing it immediately to an unexplained decimal.

The controls, geometry and timeline are meant to support the same investigation at different scales: inspect the whole diagram, pause at one event, locate its arcs in the tree and inspect the reason for the update. The surrounding searchable collections keep other studies accessible while the initial workbench remains centered on the sweep.

13 · Validation design

A correct filled image is not enough

The workbench can construct final cell polygons independently by clipping each site's viewport polygon against pairwise bisector half-planes. This produces a helpful reference picture, but it is a separate computation. If a sweep edge is wrong, the reference-filled image can still look correct. The interface therefore distinguishes the reference cells from the sweep-derived edge output.

The raw-sweep view retains the engine's edge construction with explicit endpoint welding and viewport resolution for unfinished rays. An A/B comparison identifies matched, wrong and missing edges within a configured tolerance. Raw here means sweep-derived with documented endpoint cleanup; it does not mean an untouched event trace. The clipping reference also uses floating-point calculations and tolerances.

Structural validation asks a complementary question. The arc validator checks agreement between tree and thread links, parents, head/tail and stored metadata. Some mutation snapshots occur before rebalancing, so it deliberately does not certify every AVL, treap or red-black balance condition. A clean structural ribbon, matching edge counts and matching geometry are three different kinds of evidence, and the project benefits from displaying them separately.

Reference versus result

Reference clipping is an independently organized comparison, not certified exact geometry. Its per-site pairwise clips also operate on changing polygons, so counting the pair loops alone does not establish a total O(n²) implementation bound.

14 · Build, inspect, compare

A reproducible route through the workbench

The browser target compiles the current C++ engines and Dear ImGui application through Emscripten. The native and browser builds remain separate validation targets, including their arithmetic representations and available studies. Browser modes requiring unported desktop volume shaders or worker-thread behavior are excluded instead of being presented as working equivalents.

The checked browser core suite contains 26 applicable signature groups covering degeneracies, snapshots and event storage, topology fixtures and incremental/rebuild parity. Its 20 deterministic random Apollonius cases are useful canaries, but that random test currently logs invariant failures rather than always making them fatal. A successful process exit is therefore read together with the actual reports. The named preset and lens-repair checks provide harder assertions for their bounded cases.

A practical investigation begins with one ordinary sweep, then an equal-y or cocircular fixture, and then a backend change on the same sites. Compare the raw sweep with reference clipping before moving to weighted insertion. The question at each step is what state changed, what invariant was checked, and which computation produced the image. That route makes both the implemented strengths and the remaining research work visible.

The browser presentation uses the bundled Playfair Display and Fortune Mono Medium faces, the latter a licensed static weight-500 derivation of Source Code Pro, a high-density font atlas and a separately scaled framebuffer. Browser edition reports loaded fonts and actual backing dimensions and offers an explicit density override. The pointer and layout remain in CSS coordinates, so display sharpness can change without changing the meaning of the controls.

  • Pause at a site split and connect the two surviving arc pieces to their shared input site.
  • Inspect a pending circle event, then follow an insertion that invalidates its neighborhood.
  • Compare the same cocircular input across representations and inspect both structural reports and sweep-derived edges.
  • In weighted geometry, compare direct metric winners with DCEL ownership before interpreting the filled image.
  • Treat native tests, browser core tests, font/input tests and visual interaction checks as complementary evidence.
Further work with a clear purpose

The most valuable next steps are certified evaluation for unresolved predicates, independent geometric oracles, stronger boundary-focused adversarial tests, stable-state balance checks and a local Apollonius topology update. These address the remaining numerical and structural limits.

15 · Availability and numerical boundaries

Which studies run in the browser?

The browser application compiles the C++ engines and Dear ImGui interface through Emscripten. Fortune, weighted geometry and the conceptual 3D sweep are available. The last is sampled geometry drawn through ImGui, so it has a different presentation path from the native volume viewers in Theory Workbench.

Lazy Exact is included. The regular twelve-site circle can still produce missing or misplaced raw-sweep spokes, even with that mode selected. Matched native and browser runs have shown this simultaneous-event boundary; different target arithmetic can change its appearance. This is an implementation limitation to inspect, not evidence that WebAssembly disables the mode.

Browser and desktop are separate validation targets. This Emscripten build tests 53 significand bits for double and 113 for long double, so “the browser has less precision” would be the wrong blanket explanation. Different arithmetic representations can change an event tie; unported desktop GLSL volume viewers and native worker paths are separate compatibility limits. A case that works on desktop still deserves a browser check.

Why some viewers remain desktop-only

The current site uses WebGL2. Three-dimensional textures and volume rendering are not inherently desktop-only techniques. The obstacle here is the unported renderer and execution setup, not a claim that browsers cannot represent a 3D volume. The conceptual sampled 3D sweep remains available, but is not a complete 3D Fortune solver.

From the Crystal prototype to an implementation laboratory

Earlier work → current system

The original Crystal/SFML project made the beachline and its tree visible together. Its video and event diagrams capture the starting point: understanding how a geometric transition becomes a concrete data-structure mutation.

I wrote the original Crystal implementation and the main C++ tree and beachline infrastructure without AI assistance.

The C++ project expands that investigation with multiple balance policies, recorded mutations, explicit comparisons and a wider study library. The earlier essay is preserved as an archive. Its broad correctness claims are superseded by the current raw/reference evidence and documented numerical limitations.

Current scope

  • The visualizer records execution snapshots for playback; its frame rate is not an algorithm-throughput benchmark.
  • Filtered and formula-preserving arithmetic does not constitute certified exact predicates, constructions or event ordering. The weighted-diagram implementation remains incomplete.
  • Lazy Exact is available in WebAssembly. It retains formulas and refines selected comparisons, but does not certify exact constructions or event ordering. The regular 12-site cocircular case can fail in both native and browser runs.
  • The dense interface deliberately prioritizes a complete view of the algorithm. Dedicated visualizers elsewhere in the portfolio trade that generality for a more focused presentation.
  • The browser is a selected C++/WebAssembly port, not a desktop-parity guarantee. Arithmetic representations and enabled features differ by target; difficult inputs must be checked separately. The known cocircular failure is shared by both targets, not evidence of missing browser precision alone.
