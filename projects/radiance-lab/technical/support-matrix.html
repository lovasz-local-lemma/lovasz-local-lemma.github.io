Estimator support & limitations

A branch-level account of supported materials, emitters, media, path classes and known correctness gaps.

← RadianceLab brochureTechnical reading roomRendered evidence ↗
◈

Implementation notes describe the native application. A working experiment, an approximate preview and a general transport estimator establish different things; each document states its own scope.

Audit date: 2026-09-13. Baseline inspected at 13cc7d6, followed by the additive mesh-sheet preview, PP33 surface curves, scene-translation measurement, support/volume laboratories and enhanced raster appearance. This is a call-path review, not a new numerical validation of every integrator. “Implemented” means executable code is connected to the selected mode. It does not by itself mean unbiased, complete, or fast. The validation record distinguishes numerical checks, native captures and timing experiments. Existing measured PP results remain in their individual experiment reports.

RadianceLab has ten selectable main render modes, a richer set of GPU tracer strategies, and a separate family of photon-primitive estimators. These are three different menus. Shared scene editing and display controls do not imply that every backend implements every material, emitter, medium, camera effect, or measurement.

The ten main modes

The authoritative dispatcher is EngineRender.cpp, especially the cpuIntegratorActive block and the calls to each renderPass. CPU modes 3–8 use half-resolution films. Mode 9 can use full resolution; all remain subject to scene cost and selected quality. Moving the camera clears or invalidates the appropriate film rather than turning a slow estimator into a GPU algorithm.

GPU tracer strategies are a separate axis

lightStrategy selects naive eye tracing, NEE, NEE/continuation MIS, naive light tracing, light-tracing camera connections, BDPT, or diagnostic selections. The GPU BDPT route really builds interior connections; it is not only a collection of diagrams.

  • The older A weighting route uses bdptMISWeight in pt_bdpt.glsl, which falls back to flat 1/N even when a balance/power label is selected.
  • B balance / B power has a separate implemented path-PDF construction in pathTrace.comp, beginning at FEAT_BDPT_MIS_B. It evaluates eye-emission, NEE, light-to-camera and interior connection weights. Its scope is surface transport; the volume showcase disables it.
  • ComputePathTracer::featureMask only requests B when BDPT, a non-flat scheme, method B, and no volume showcase are selected. Shader compilation can fall back by removing FEAT_BDPT_MIS_B; inspect the log as well as the UI.
  • bdptVolumeShowcase is expressly a biased experimental volume showcase. It must not be described as a complete volumetric BDPT implementation.

These distinctions matter in a strategy pyramid: an actual rendered (s,t) contribution is evidence that the path construction runs, but a visually plausible combined image is not a proof that all PDFs and delta cases match.

Concrete medium issues to resolve before reference-grade comparisons

These are implementation findings, not general objections to the algorithms:

  1. UPBP survival weighting. deltaTrack samples extinction events using sigmaS + sigmaA. On no event, both buildLightPaths and traceEyePath multiply by another ratioTrack. In a homogeneous segment, that contribution is selected with probability T and then weighted by T again, giving T² rather than T. An absorption-only slab with a known background is a clean regression fixture. Correcting only this branch is not enough to certify the rest of UPBP.
  2. UPBP caps and merge measure. Both trackers cap at 128 steps; ratio tracking stops when T <= 0.001 without a compensating roulette rule. Volume-vertex gathering uses an r^-2 Epanechnikov expression and does not isolate a pure 3D vertex population. Connection and merging also have fixed 0.5 cross-strategy factors. These need separate measure/normalization tests.
  3. GPU null events. The main pathTrace eye-medium block samples one candidate for a volume. Its rejection continue advances the outer volume-entity loop, rather than continuing through further null events in the same medium. This differs from a complete delta-tracking loop. On the no-collision branch it also applies extra absorption. The standalone helper named deltaTrackVolume is not evidence that this main path uses it correctly.
  4. GPU shadow attenuation. pt_volume.glsl, evalVolumeTr, applies homogeneous Beer attenuation over each bounding primitive; it does not evaluate its procedural density along the shadow ray.
  5. Volume NEE measure. sampleLight in pt_light.glsl computes p_V r². This is a joint radial/directional density, not a marginalized solid-angle density. It can be used for the sampled volume integral with the corresponding distance variable; inserting it directly beside a phase-only density in generic MIS requires a matched joint measure. The generic volume-NEE MIS path needs this audit before an unbiased claim.
  6. Guiding proposal accounting. The guided branch divides by a guided/cosine mixture, while the cosine branch uses only throughput *= albedo. Hemisphere folding also requires summing densities of both preimages; the current sampler returns only the selected bin's density. These are independent of how attractive the guiding visualization looks.

The survival/ratio-tracking distinction follows the executable reference treatment in PBRT, Transmittance. The published UPBP formulation explicitly handles the different estimator measures; its guarantee should not be transferred to this implementation by name alone.

Applicability and execution are part of the experiment

  • Custom 31 checks for one homogeneous medium containing the whole sampled emitter, not just its center. Selecting any plane requires emissive quads only, so every technique covers the same source roster. It refuses unsupported medium/emitter combinations instead of pretending a partial image covers them.
  • Directional 7/8/9/13 now declare NEED_LIGHT_OR_ENTITY, matching their actual preference for ppSampleEmissiveEntity and fallback to area/point scene.lights. Uniform emitting boxes/balls are sampled in their interiors with 1/V, isotropically and without a surface cosine. This fixes an availability gate; it does not add SDF/noise-weighted emission or general heterogeneous attenuation. Forty focused assertions in ppCustomMISSelfCheck cover source admission, actual volume-origin sampling, disabled emitters, point fallback, and unchanged restrictions on 18/20/32.
  • Comp mode partitions path classes between a primary and a backup. It is different from MIS. It refuses modes such as custom31 and mesh32 whose finite-kernel/separate-pass behavior does not fit the analytic ownership claim. PPCompReport reports structural drops as well as the class declaration.
  • Correlated does not mean hardware rasterized. ppCorrelatedPass can reconstruct a primitive at every pixel; ppCorrelatedPassRecords only has frozen-record builders for quad, beam and hourglass. Directional spheres/disks/cones can therefore have expensive correlated fallback behavior even before considering projected coverage or singularities. Verify the [PP] [corr] / [PP] [raster] log.
  • Freeze pool changes which random data are refreshed. Replaying a finite fixed pool improves inspection but is not equivalent to adding independent samples forever.
  • Mesh32 fast preview, implemented separately in PPMeshSheets.inl::renderPreview with FastSheetRaster.h, uses reduced-resolution projected triangles, vertex-interpolated radiance, blur and a tangency clamp. It is a convenient viewfinder. Use the original mesh-sheet gather for numerical comparisons; neither is an exact general unbiased estimator.

Surface rendering, surface curves and derivative experiments

surfaceNEE, surfaceBSDF, surfaceSpec and the finite-radius surface photon map remain distinct from the new PP33 angular-sheet receiver curves. PP33 samples one chart coordinate, stratifies the other, traces the actual path, and projects the first non-delta receiver to the camera. Its input is angular flux; adding an incident cosine again at the receiver would double-count the angular-to-area change. The final BSDF and camera projection have their own measures. It has no diffuse continuation after that receiver and no general cross-family surface MIS.

The independent LightTranslationLab now measures a selected source translation in a snapshot of the actual scene. Matched camera/emitter random numbers produce two central finite differences at epsilon and epsilon/2. It includes direct Lambertian shading, distance/cosine changes and optional visibility changes for the ordinary analytical scene-intersection geometry, with plane-backed area sources using native emission profiles0/3 or explicit point sources. The source's triangle mesh supplies its sampled area; arbitrary mesh-only emitters are not admitted. This is a direct scene measurement with finite epsilon, not automatic differentiation of PP33 or arbitrary multibounce transport. The older analytic collimated-edge experiment remains useful alongside it; see extension assessment.

The volume estimator lab compares collision, survival track length and ratio tracking against one independent scalar reference. Its passing numerical checks validate that lab, not the existing GPU/UPBP tracking implementations. The support/time lab likewise computes restricted spatial and temporal intersections without changing native PP time support.

The new 99–102 bundle closes the guiding-learning, mutation-anatomy and paired PM/VCM scene gaps. EngineRender.cpp applies their main-mode enable flags, camera, exposure and backend settings, and disables stale auxiliary renderers when loading a paired preset. Startup configuration can override the mode; explicit menu selection reapplies the pair. This is launch-path evidence, not a substitute for runtime image checks or convergence measurements.

The follow-up 103–109 bundle adds controlled fog/source comparisons and native surface receiver paths. Enhanced-raster A/B fixtures now exist. Remaining presentation gaps include a dedicated fitted-LTC/baked editing workflow, a native UPBP tracker/merge diagnostic after its weighting issues are addressed, and a clearly labeled specular-mutation study for mode8. The independent tracking lab covers the underlying laws; it does not close UPBP's production correctness gap. Missing algorithms such as Newton manifold solving or full surface-sheet MIS are a separate backlog and should not be filled with a misleading preset name.

How to keep this matrix current

Start with EngineRender.cpp and follow the selected function into its implementation. Check scene filtering, source selection, probability density, BSDF/phase evaluation, visibility, accumulation and feature masks. Search both definition and callers: DiffRenderer.h, Holography.h, pmGPUTrace, and the unused Newton configuration show why a declaration or attractive control panel is insufficient evidence.

New scene bundles and native experiments should cite their specific backend and path class. A screenshot proves a configuration produced an image; it does not settle bias, completeness, convergence, or speed outside that configuration.
