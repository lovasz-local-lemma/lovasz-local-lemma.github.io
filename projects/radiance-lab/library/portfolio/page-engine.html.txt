<section id="twopaths" style="--secc:var(--l400)" data-nav="Two paths">
  <div class="wrap">
    <div class="narrow">
      <p class="sec-label">01 — Shape of the thing</p>
      <h2>The two renderers do not even share their intersection code</h2>
      <p class="lead">A scene is a flat list of entities with analytic primitive types. It is uploaded to the GPU as four hand-packed SSBOs, and it is walked directly on the CPU by a 169-line intersector. Those are two separate implementations of the same five shapes, written at different times, and that independence is what makes a number produced by one of them count as evidence about the other.</p>
      <p>Ten transport modes sit on top of that one scene — the GPU megakernel in real time, eight CPU integrators interactively, and a rasteriser. Number keys switch between them; the viewport keeps its camera and its film. Nine of the ten write the same linear-HDR film, and the headless harness dumps that film in one format — a four-byte magic, three ints, then <span class="mono">w·h·3</span> floats — so a GPU frame and a CPU frame are directly subtractable.</p>
    </div>

    <div class="narrow">
      <p class="note"><b>Mode 0 is not only a viewport.</b> The raster panel carries a <b>tracer-guided rasterizer</b> — a toggle and a two-way mode, screen-space blend or vertex-baked, which reprojects the tracer’s own colour onto rasterised geometry and blends it over the raster shading so direct lights still contribute; the second mode is there for painterly and data-mosh passes. Beside it sits an experimental <b>LTC area light</b>, linearly transformed cosines after Heitz et al., which stands down to a legacy fallback light the moment the scene has a real quad light of its own. Both have readers in the raster renderer, both are one click from the panel, and both are <span class="st st-c">never viewed</span>: no capture of either exists anywhere in this repository. They are on this page because the honest thing to do with a working feature nobody has photographed is to name it, not to quietly leave it out of the mode table’s one-line summary.</p>
      <h3>The mode number is a request, and the strategy number is not the one in the combo</h3>
      <p>Neither selector on that panel behaves the way a radio button usually does. A mode change is <b>queued rather than applied</b>: the click sets a pending target and a three-frame cooldown, the radio shows the target instead of the state, the viewport prints "switching to&hellip;", and only when the counter reaches zero does the engine call <span class="mono">glFinish</span> and invalidate all eight CPU integrator instances — including the split view's second photon-primitive integrator — before the mode actually changes. Three frames of latency, bought to avoid freeing a resource the GPU is still reading.</p>
      <p>The light-strategy combo is stranger: its display order is not its enumeration. Seven entries map through <span class="mono">comboToStrategy[] = {0, 1, 7, 2, 3, 4, 5}</span>, because internal ID 6 used to be the photon mapper and is now an overlay with a tab of its own — and a saved configuration still carrying strategy 6 is silently rewritten to Naive on load.</p>

    <div class="narrow">
      <h3>What they share, and what they diverge on</h3>
      <p>The shared surface is narrow on purpose, and it has been audited. Two places where the two implementations of the same primitive do not describe the same object, both known and both bounded:</p>
      <ul class="clean">
        <li><b>A rotated box is a different solid to each renderer.</b> The GPU treats <span class="mono">Box</span> as an OBB and rotates the ray by the entity's quaternion; the CPU intersector has an AABB path only. Any scene with a tilted box is outside the comparison.</li>
        <li><b>Every bounded plane is 0.04 wider than it is declared.</b> Both intersectors clip with <span class="mono">diff &gt; halfExt + 0.02</span> per axis, deliberately mirrored so the two agree. An estimator that reads an emitter's area from an intersection therefore integrates over a quad of side <span class="mono">2h + 0.04</span> and reads 8–15% high on presets 47, 48 and 52. The pad was left global because removing it is not byte-neutral for any strategy in the roster.</li>
      </ul>
    </div>

<section id="megakernel" style="--secc:var(--l460)" data-nav="Megakernel">
  <div class="wrap">
    <div class="narrow">
      <p class="sec-label">02 — The kernel</p>
      <h2>The path tracer recompiles itself when the render state changes shape</h2>
      <p class="lead">The whole real-time path is one compute shader, 4,090 lines and 229 KB, and one <span class="mono">glDispatchCompute</span> per frame — bidirectional path tracing, fourteen materials, spectral transport and participating media in a single dispatch. A megakernel that large is slow to compile and, on some feature combinations, does not compile at all, so the engine specialises it rather than compiling all of it: it derives a four-bit feature mask from the live render state, builds a <span class="mono">#define</span> list from the mask, and rebuilds the kernel only when the mask changes.</p>
      <p>The consequential detail is the last line of the recompile block: when a new variant loads, the accumulation buffer is reset, with the comment saying why. The image the user was accumulating was computed by a different estimator, and averaging the two would be quietly wrong. Turning spectral mode on therefore costs you your converged frame, visibly, rather than silently corrupting it.</p>
    </div>

    <div class="formula">
      <div class="f">mask = <span class="hl">BDPT</span> | <span class="hl">SPECTRAL</span> | <span class="hl">VOLUMES</span> | <span class="hl">BDPT_MIS_B</span></div>
      <div class="n">Derived from lightStrategy, spectralMode, enableMedium &amp;&amp; sceneHasVolume, and the BDPT MIS selection.<br><span class="mono">ComputePathTracer.cpp:81</span> · defines at <span class="mono">:98</span> · recompile at <span class="mono">:1703</span></div>
    </div>

    <div class="narrow">
      <h3>The ladder, and the measurement that put a rung in it</h3>
      <p>A compile failure at this size is a real operating condition, not a theoretical one, so the recompile is a measured ladder rather than a single call, and every rung is a state the renderer keeps running in:</p>
      <div class="readout">
        <div class="row"><span class="lbl">1 — full requested mask</span><span class="val">compile</span></div>
        <div class="row"><span class="lbl">2 — on failure, drop <span class="mono">FEAT_BDPT_MIS_B</span></span><span class="val">BDPT survives, flat MIS</span></div>
        <div class="row"><span class="lbl">3 — on failure, mask 0</span><span class="val">minimal kernel, always fits</span></div>
        <div class="row hi"><span class="lbl">4 — on failure, keep the previously-compiled program</span><span class="val">no reset, no crash</span></div>
      </div>
      <p style="margin-top:26px">Rung two exists because a combination was measured to fail. The source records it in the mask function rather than in a commit message:</p>
    </div>

    <div class="formula">
      <div class="f" style="font-size:clamp(12px,1.7vw,15px);text-align:left;line-height:1.7">// Measured: method B + FEAT_VOLUMES exceeds the GPU instruction<br>// ceiling, so on volume scenes method B is not requested.<br>// All other combos fit.</div>
      <div class="n"><span class="mono">ComputePathTracer.cpp:88</span> — so the mask function refuses to request the combination in the first place, and the ladder's second rung is the safety net for hardware other than the one it was measured on.</div>
    </div>

    <div class="narrow">
      <p>Startup deliberately compiles mask 0 rather than the mask the scene will want, because the minimal variant always fits and always starts fast; the first frame pays for the specialised one. Shaders are re-read from the build output at launch, so a shader change is a 6–14 second cycle with no rebuild of the C++.</p>
      <p class="note"><b>The failure mode is louder headless than interactively.</b> If even mask 0 fails, the application keeps running with no path tracer and logs one line. Headless that is fatal, because no film is written and the harness notices. On screen it just looks wrong.</p>
    </div>

<section id="geometry" style="--secc:var(--l500)" data-nav="No BVH">

    <div class="narrow">
      <p class="sec-label">03 — Geometry</p>
      <h2>Every ray tests every primitive, and that is the design</h2>
      <p class="lead">There is no acceleration structure in the path tracer and no triangle in the scene, and both are decisions. <span class="mono">traceRay</span> is a linear scan over all primitives, and the volume interaction runs a second full scan per bounce. <span class="mono">tinyobjloader</span> is vendored and linked and appears in zero source files; not one triangle reaches the <em>path tracer</em>. It is worth the italics: the tracer's upload loop skips every entity whose primitive type is <span class="mono">None</span>, while the rasteriser uploads a GPU mesh for every entity that owns one, so an entity can carry both a triangle mesh and an analytic primitive and be a different solid to each renderer. One preset exercises exactly that, and the note below the acceleration table is what happens when it does.</p>
      <p>The reason is not performance. It is that the analytic estimators this engine exists to serve need <em>exact</em> intersections, and one of them needs more than that. The photon hourglass sweeps a refracted photon about the axis running from the light to the sphere's centre, and its whole derivation rests on that revolution being an exact symmetry of the object. A tessellated sphere is not rotationally symmetric. It would not merely make the estimator slower; it would make it wrong, in a way that would show up as a bias nobody could localise.</p>
      <p>So spheres, bounded planes, oriented boxes, volume spheres and volume boxes are the entire palette; every intersection in every frame is exact, and forty-nine scene presets are composed procedurally from it.</p>
    </div>

Ten of them are on the material showcase. The other four had no preset at all until the Apothecary (preset 56, a GPU-only room) was written to carry them: dipole subsurface on its jars, anisotropic brushed metal, hair, and passthrough on every volume prop. An earlier version of this page counted ten reachable and four unreachable; the catalogue caught the page predating the preset.</p>

      <p>The panel that edits those fourteen branches is not a stack of sliders. Its Surface tab runs a thousand lines and contains three plotters that no figure on this site has ever shown, each of which would be a feature in most renderers:</p>
      <ul class="clean">

      <p>Three smaller pieces of the same panel are worth the sentence they take. <b>Anisotropy angle</b> is a separate slider from anisotropy amount, so a brushed metal's grain can be rotated independently of its strength — and it is the one field of the anisotropic branch that is <span class="st st-c">never viewed</span>. <b>Negative emission</b> unlocks a signed strength slider per material and per volume, and one preset ships a sphere at &minus;10 &mdash; but the subtractive light does not arrive, and finding out took one grep.     </div>

<section id="spectral" style="--secc:var(--l580)" data-nav="Dispersion">
  <div class="wrap">
    <div class="narrow">
      <p class="sec-label">05 — Spectral</p>
      <h2>Dispersion is gated on the spread parameter, not on the material type</h2>
      <p class="lead">The surprising fact first, because it catches people: plain <span class="mono">Glass</span> disperses. The branch that computes a wavelength-dependent index tests <span class="mono">dispersionSpread &gt; 0.001</span> and nothing else, so a material typed as ordinary glass with a non-zero spread refracts chromatically, and a material typed <span class="mono">DispersiveGlass</span> with zero spread does not.</p>
      <p>Underneath is a full spectral pipeline. The engine carries a hero wavelength per path — one λ drawn uniformly from [380, 780] nm at the top of the eye path, stored so a bidirectional connection can reuse it. Spectral reflectance is up to eight Gaussian lobes per material, packed into the material SSBO and edited in the interface on a rainbow-backed canvas that replaces the albedo picker. Conversion back to RGB goes through the CIE 1931 curves with an explicit normalisation so an equal-energy white matches the luminance the RGB path would have produced.</p>
    </div>

    <div class="formula">
      <div class="f">n(λ) = ior + <span class="hl">B</span>/λ² − <span class="hl">B</span>/0.589²&nbsp;&nbsp;&nbsp;&nbsp;<span class="hl">B</span> = (ior − 1)·0.01·spread</div>
      <div class="n">Cauchy, referenced to the sodium D line. Physical B for common glass is about (ior − 1)·0.01; the spread slider is an honest exaggeration factor, not a hidden fudge.</div>
    </div>

    <div class="narrow">
      <h3>Two estimators for one physical effect</h3>
      <p>Spectral mode feeds the hero wavelength straight into the Cauchy expression. RGB mode cannot — there is no single wavelength — so it runs a channel-level Monte Carlo instead: pick one of R, G or B uniformly, use that channel's wavelength, weight the throughput by three and zero the other two. The G wavelength is not fixed at 540 nm but slides between the R and B anchors under a slider, which is a control with no physical meaning that exists because it makes the fan easier to read on screen.</p>
      <div class="readout">
        <div class="row"><span class="lbl">Hero wavelength, per path</span><span class="val">380 + 400·ξ nm</span></div>
        <div class="row"><span class="lbl">Spectral reflectance</span><span class="val">≤ 8 Gaussian lobes / material</span></div>
        <div class="row"><span class="lbl">RGB dispersion estimator</span><span class="val">1 of 3 channels, ×3 weight</span></div>
        <div class="row"><span class="lbl">R / B anchors</span><span class="val">620 nm <span class="d">/</span> 460 nm</span></div>
        <div class="row"><span class="lbl">Sky in spectral mode</span><span class="val">achromatic</span></div>
      </div>

      <h3>Where a medium is actually authored, and the two panels that cannot read each other</h3>
      <p>All seven of those sources are reached through one panel — Properties, four tabs, the place an entity stops being a shape and becomes something with physics. One button is an entire medium, not a texture.</p>
      <p>The finding underneath that is the more interesting one. The Noise Lab in the node editor and the Noise Lab in this panel author the same kind of object into <strong>two disjoint halves of one per-primitive GPU record</strong>. The panel fills one block of it from the entity's own noise configuration; the node fills a different block from the node's parameter array.       <p>Volume next-event estimation is skipped for the Mie and Rayleigh branches, because neither has a closed-form evaluation available at that call site. They render by phase sampling only. That makes them <em>noisier by construction</em>, which is a different statement from noisier by defect, and it is why a Mie fog box needs several times the passes of an HG one to read as clean.</p>

<section id="lights" style="--secc:var(--l620)" data-nav="Light &amp; bounces">
  <div class="wrap">
    <div class="narrow">
      <p class="sec-label">07 — Sampling and counting</p>
      <h2>A point light is never sampled at a volume scatter vertex — and that is why the estimator research exists</h2>
      <p class="lead">The delta point-light connection appears at exactly one site in the megakernel, inside the surface shading block. There is no counterpart in the volume scatter branch. A scene lit by a point light and filled with fog therefore renders near-black on the GPU: the only way a camera ray in the medium can find that light is to hit it by chance, and it has zero measure.</p>
      <p>That is not a bug in the tracer. It is the shape of the problem the photon-primitive family was built to solve, and it is the reason this engine's most-used reference is a stochastic photon beam rather than next-event estimation.</p>
    </div>

    <div class="narrow">
      <h3>What the GPU does sample well</h3>
      <ul class="clean">
        <li><b>Sphere lights by solid angle.</b> Sampling is uniform over the cone the sphere subtends, giving a constant pdf and no samples wasted near the silhouette. The older hemisphere-area sampler is retained behind a flag, which makes it a clean variance-only A/B: same image, different noise.</li>
        <li><b>Power-weighted light selection.</b> Three modes — uniform, area-weighted, and area × luminance. The Veach MIS scene selects power weighting automatically, because its lights span roughly 500× in emission and 500× in area and uniform selection there is a disaster.</li>
        <li><b>Quad lights by the right edges.</b> Each in-plane edge is paired with the half-extent of the world axis it points along, not by array position — so a non-square light is sampled correctly.</li>
        <li><b>Multiple importance sampling at three sites</b> — BSDF-hits-emitter, surface NEE, and volume NEE — all with the power heuristic at β = 2.</li>
      </ul>
      <p>Five emission profiles sit on the emissive material itself, each with a polar tilt and an azimuth: diffuse cosine, laser at <span class="mono">cos<sup>500</sup></span>, cone with a hard cutoff, uniform hemisphere, and a grazing-only ring. <b>Cone and ring are used by no preset at all.</b> They are not invisible, though — the Properties panel draws whichever profile is selected as a three-dimensional lobe you can right-drag to rotate, with a power read-out beside it, which makes it the one place in the program where a light's goniometric diagram and the light itself are the same object. Like the profiles it draws, it has <span class="st st-c">never been viewed</span>.</p>
      <p>Volume emitters get their own next-event path, switched on automatically by two of the three config-only fog boxes &mdash; presets 39 and 43, the cube-light and ball-light rigs &mdash; so an emissive volume is sampled rather than found. It samples a point uniformly inside the shell (<span class="mono">r&middot;u<sup>1/3</sup></span> in a sphere, uniform in a box), evaluates the density there, and converts the volume density to solid angle by <span class="mono">p<sub>vol</sub>&middot;r&sup2;</span> with no cosine at the light, because there is no surface to have one. And it carries a consequence the profile list does not advertise: the sampler sets the emitter's material index to &minus;1 on purpose, so <b>an emissive volume has no emission profile</b>. All five belong to surfaces.</p>
    </div>

    <div class="narrow">
      <h3>The five-branch profile is written out five times, and one copy disagrees</h3>
      <p>The tidy version of this is that the profiles are evaluated identically wherever a light is used. The source is one shared function and <b>four hand-transcribed copies</b>: <span class="mono">evalEmissionProfile</span> in a module, called from light tracing and from two connection sites, and the same five-branch ladder written out again inline in four more places — a volume next-event branch, a surface next-event branch, a light-to-aperture connection, and the site where an eye path hits an emitter directly.</p>
      <p>Four of the five agree. The fifth — the emitter-hit copy, the one that runs when you simply <em>look</em> at a light — writes the diffuse profile as <span class="mono">abs(dot(rd, n))</span> where every other copy writes <span class="mono">max(dot(&minus;&omega;, n), 0)</span>, and writes the ring as <span class="mono">1 &minus; abs(&middot;)</span> where the others clamp. So a diffuse emitter is <b>two-sided when it is looked at and one-sided when it is connected to</b>. That absolute value is the same view cosine §01 of this page reports as the unresolved 2.96&times; disagreement between the two renderers; naming it here says what it is structurally, which is a fifth transcription that drifted, not a convention anyone chose.</p>
      <p class="note"><b>And the plot beside them is a sketch, not an evaluation.</b> The goniometric visualiser draws each profile from its own drawing code rather than from the function the renderer evaluates, and for the ring the two do not match: the panel draws a lobe of length <span class="mono">sin&sup3;&theta;</span>, while the shader evaluates <span class="mono">3(1 &minus; cos&theta;)&sup2;</span>. Both peak at grazing and they fall off differently. The read-out labelled <em>Power</em> is <span class="mono">mean(emission RGB) &times; emissionStrength</span> — no area, no solid-angle integral — so it is a radiance, and two emitters of wildly different size read the same number. Arrow lengths are normalised per profile as well, which hides that the ring's peak weight is 3 where the diffuse profile's is 1.</p>
    </div>

      <h3>The bounce control is a teaching instrument</h3>
      <p>The newer of the two bounce models does not count ray segments. It counts <em>scatter events</em>, separately by type, with a clean reading:</p>
      <div class="readout">
        <div class="row"><span class="lbl">Surface = 0</span><span class="val">emitters only</span></div>
        <div class="row"><span class="lbl">Surface = 1</span><span class="val">direct illumination</span></div>
        <div class="row"><span class="lbl">Medium = 1</span><span class="val">single scatter</span></div>
        <div class="row"><span class="lbl">Medium = 0</span><span class="val">ray passes through the fog</span></div>
        <div class="row hi"><span class="lbl">Optional total budget</span><span class="val">caps the sum, not each type</span></div>
      </div>
      <p style="margin-top:26px">Being able to set surfaces to zero and mediums to one, and see exactly the single-scatter term and nothing else, is what makes a light-transport bug findable. The legacy single-counter model is still selectable, and the two disagree about what "two bounces" means — which is worth knowing before comparing anyone's numbers to anyone else's.</p>
    </div>

      <h2>What is wrong with the engine, in the same table as what is right</h2>
      <p class="lead">Everything on this page above the line was built; this is the part that is not finished, and the single most consequential item comes first because it is a bias source and the rest are not.</p>
      <p><b>The eye path has no Russian roulette.</b> The one roulette block in the megakernel is inside the light subpath. The eye path terminates on the bounce ladder alone, and the estimator is bounded instead by a hard clamp: <span class="mono">radiance = min(radiance, vec3(1000.0))</span>, with further clamping inside the light-tracer splat. That clamp is a bias with no counterpart in any of the CPU integrators, which declare their bias and measure it. Its effect on any image here has never been measured — so a GPU frame used as a reference is, strictly, a reference with an unquantified ceiling on it.</p>

The temporal EMA and spatial Gaussian are labelled blur, not denoise, for the same reason.</p>

      <h3>One more thing the harness cannot see</h3>
      <p>A single preset sets a focal length, and until it was fixed that value leaked: load that scene, then any other, and the rest of the session rendered at a 30% wider field with nothing on screen saying so. The byte-identity regression harness — eight films, two resolutions, a feature off must change nothing — is <b>structurally blind to that entire class of bug</b>, because every headless render launches a fresh process and so never loads two presets in sequence.</p>
      <p>That is the most useful thing in this section. A validation apparatus has a shape, and the shape is a claim about what it cannot catch. Anything a preset writes and no preset resets is invisible to this one.</p>
