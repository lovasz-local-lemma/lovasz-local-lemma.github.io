The same core, in a browser.

Fortune and the weighted-diagram kernels are compiled from the current C++ source. Playback uses recorded engine snapshots; the diagram and trees expose that recorded state.

Arithmetic: this WebAssembly build uses 53-bit double and 113-bit software long-double significands. Wider evaluation and retained formulas are useful numerical tools; neither provides certified exact predicates.

Known cocircular boundary: a regular ring with a site at the sweep’s lowest point makes that site event simultaneous with several circle events. The current browser and native engines can leave a missing or misplaced spoke. Lazy Exact refines selected signs and retains formulas; it does not supply exact constructions or symbolic event ordering. Open the 12-site stress case ↗

Opening the selected study…

Changing this selection reloads the collection’s starting study. Inside the workbench, collection buttons filter the algorithm picker; search can span collections.

Supported dimensional studies: the conceptual 3D sweep samples a paraboloid beach surface; it is not a complete 3D Fortune solver. The 2D FFT and filter bank compute image spectra and reconstructions. Gaussian fitting runs the same analytic-gradient Adam kernels serially on the CPU, fitting a 2D image.

Excluded from this browser picker:

  • 3D FFT volume, 4D FFT, 3D FFT filter bank, KLT eigenvolumes and voxel/JFA 3D Voronoi: their shared desktop volume renderer uses GLSL 330, not WebGL2’s GLSL ES. That shader and rendering contract has not been ported. The 3D filter bank also starts native workers; larger 4D transforms do too. Compiling the CPU FFT kernels alone does not make these visual modes available.
  • Standalone linear-programming interface: not validated in the browser. This is a validation boundary, not a claim that the CPU solver needs desktop graphics.
  • Original Crystal/SFML application: native runtime, OS window and libraries; its desktop launcher cannot run inside this WebAssembly application.
