Technical Reference

A developer-level walkthrough of the engine: the data model, every module's algorithm, and — in full — the ordered routine the integrator follows. Companion to the narrative History pages. Method names, constants, and orderings below are taken from the source in symbolic/.

One-paragraph summary. A pure-Ruby CAS on a binary-tree AST. Differentiation is exact rule-based recursion. Integration is a deterministic heuristic cascade of ~17 ordered phases (not Risch), each gated by a structural predicate; the first to return a marker-free result wins, and anything unsolved becomes an honest integral(…) marker. Completed candidate antiderivatives carry a Monte-Carlo derivative check (d/dx of the answer vs the integrand). This numerical spot-check can detect errors; it is not an identity proof, and a sample agreement percentage is not a probability of correctness. A Sinatra server (or, for GitHub Pages, an in-browser ruby.wasm VM) drives a zero-dependency vanilla-JS frontend.

1 · Architecture, object model & data flow

Every request follows one pipeline. The expression is parsed once and stored server-side (or VM-side) by id; operations transform the stored tree, and integrals pass through the verifier before serialization.

text→ Parser→ AST→ operation module→ Normalize / Simplify→ Verify (MC)→ JSON→ render

The core class MathematicalExpression includes every capability as a mix-in module, so one object answers .derivative, .integrate, .series_expand, .try_residue_integration, etc. Most phases are gated by respond_to?(:method, true) — a module that is required but not included is silently skipped (a bug we hit twice). Instance flags @use_experimental_integration and @use_experimental_simplification select the aggressive paths.

Object model

The whole engine rests on six plain Ruby types with no inheritance — structure is by composition and mix-in, never subclassing. The AST node is self-referential (its left/right are themselves ExpressionNodes); the parser builds those trees; the facade owns one root node and folds in every capability module.

Capability modules

The 20 modules MathematicalExpression mixes in are grouped below by concern. Because they are included, every one becomes an instance method on the single facade object, and phases call their siblings through respond_to?. The seven POST modules are a different animal: standalone module_function services the transport layer calls directly — they are not mixed into the facade.

The two transports — one engine

The same engine code runs two ways. Natively, a Sinatra server answers /api/*. On GitHub Pages there is no server: wasm_runtime.js shims fetch so the identical paths route into an in-browser ruby.wasm VM, where Engine.solve (wasm_dispatch.rb) mirrors every Sinatra route. Both paths construct the same MathematicalExpression and produce identical results.

1.5 · The six self-contained tools — what each one does

Most operations in the right-hand panel act on the formula in the input bar. Six do not: they open a dialog carrying their own inputs, and the panel separates them under self-contained · own inputs. They are the least self-explanatory part of the engine, so here is what each actually computes and how. Vector calculus joined this group when it stopped being able to work from the bar alone — divergence and curl consume a whole vector field, which has to be typed (§14).

⟦f⟧ Interval bounds conditional

What it does: carries bounds over a whole region. The enclosure guarantee for transcendental functions is conditional on the platform math-library error bound. Three modes: the range of f over a box, its global minimum, and a bracket around a definite integral.

How: a third evaluator, evaluate_interval, walks the same AST as ordinary evaluation but carries [lo, hi] bounds through every operation with outward rounding — basic-operation results widen by one ULP; transcendental results widen by two, assuming that covers the platform library error. Subdivision can tighten dependency overestimation. The global minimum uses branch & bound: if a box's interval lower bound exceeds the best value found so far, that box provably cannot contain the minimum and is discarded. This can retain narrow dips missed by point sampling, though finite search budgets can leave wide bounds.

Why trust it: 4 000–20 000 sample comparisons and an independent Simpson estimate check for regressions. Passing these checks does not establish the transcendental library assumption. Full detail in §18.

Q Exact ℚ, ℚ(α) — exact arithmetic proven

What it does: computes with no rounding error at all, or refuses. Four modes: compare float vs interval vs exact on one expression; float-only (what the engine did before); exact-only; a polynomial lab (GCD, squarefree decomposition, resultants); and ℚ(α), arithmetic in an algebraic extension.

How: evaluate_exact returns a Ruby Rational — 0.1 + 0.2 is exactly 3/10 — and returns nothing at all when no rational answer exists (√2, sin 1, e). For ℚ(α), an element is a polynomial in α reduced modulo a minimal polynomial, so √2 is stored as the symbol α plus the rule α² = 2; squaring it gives exactly 2 where a float gives 2.0000000000000004. Inverses come from the extended Euclidean algorithm in ℚ[x].

Why it matters: "is this coefficient zero?" is a guess at 1e−10 in floating point and a fact in ℚ. Every decision procedure is built out of exact zero-tests. The demo worth trying: gcd((x−1/3)⁴, f′) is degree 3 exactly, and the float path returns degree 0 — "no common factor" — which is structurally wrong, not merely imprecise. See §20.

ẋ=Θξ Discovery — SINDy verified

What it does: runs the engine backwards. Given only a trajectory — a table of numbers — it recovers the differential equation that produced it.

How: build a library Θ(x) of candidate terms (monomials, optionally sin/cos), estimate ẋ from the data, then solve Ẋ = Θ(X)·Ξ for sparse Ξ by sequential thresholded least squares: solve, zero every coefficient below λ, re-solve on the survivors, repeat. Sparsity is the prior that turns a curve fit into a candidate physical law.

Why trust it: the discovered model is judged by oracles the regression never saw — agreement with the true vector field at every sample (the verdict), plus RK4 re-simulation (corroboration). Lorenz comes back exactly, −8/3 included. Remove sin from the library and ask for the pendulum, and it reports FAILED with the fabricated terms flagged rather than presenting a plausible polynomial. See §17.

gμν Relativity — symbolic differential geometry verified

What it does: takes a spacetime metric and derives its curvature — Christoffel symbols, Riemann and Ricci tensors — then flies a test particle along a geodesic.

How: every quantity comes from the engine's own symbolic derivatives, composed through parseable infix, so parameters like mass M stay symbolic in the output (Γttr = M/(r(r−2M))). The orbit is RK4 integration of ẍ^μ = −Γ^μαβ ẋ^α ẋ^β on those computed symbols.

Why trust it: Schwarzschild must be a vacuum (all ten Ricci components vanish) and its Kretschmann scalar must equal 48M²/r⁶ — a nonzero oracle, so "everything came out zero" cannot fake a pass. De Sitter must satisfy Rμν = 3H²gμν, whose sign pins the curvature convention. Along the orbit, energy, angular momentum and the 4-velocity norm must stay conserved. Mercury's numbers in the verified formula give 42.98″/century. See §19.

∮∬∭ Field Theorems & Moving Domains EXPERIMENTAL

What it does: a launcher for seven numeric tools — line integrals (work/flux/arc-length), surface integrals, Green's, Stokes' and Gauss's theorems, the Leibniz rule in 1D/2D/3D, Reynolds transport, and the Lebesgue integral.

How: tangents, curls and divergences are symbolic; the domain integrals are Monte Carlo or quadrature. The transport tools use a flow-map identity — a fixed unit ball mapped by φt(u) = c(t) + A(t)u — so the boundary-motion term comes from symbolic det(A)′ and ∇f rather than surface quadrature.

What kind of evidence stands behind it: this is the one group not checked against closed forms. Each instead computes its quantity two independent ways and shows they agree (e.g. a line integral directly versus Green's theorem over the enclosed region), which is strong evidence but weaker than an oracle. They also carry Monte-Carlo noise, so results wobble in the last digits. Laurent sits in the same category: its pole order is detected numerically and unstable coefficients truncate the series rather than being trusted.

Why there is no E badge on the buttons. An earlier build tagged the numeric tools with a small E. It was dropped, because it labelled the wrong thing: for these tools the closed forms are standard and not in doubt — what varies is the quality of the evaluation (Monte-Carlo noise, numerically detected pole orders, sampled derivative stencils). A single badge on the button could not say which, and it competed with the per-result verdict, which states the actual evidence far more precisely: conditional interval bounds, verified against an oracle, corroborated two ways, or FAILED. Read the verdict on the result, not a badge on the button.

1.6 · Every mode, and what stands behind it

Twenty-three operations are reachable from the panel: sixteen buttons, and seven more inside the Field Theorems launcher. The sections that follow go deep on the subsystems; this one is the index — what each mode eats, what it hands back, which module does the work, and above all what kind of evidence supports the answer. That last column is the one to read first, because the modes differ far more in how well they are checked than in how hard they are.

Five kinds of evidence. CONDITIONAL INTERVAL BOUND — an outward-rounded enclosure; transcendental guarantees assume the platform library error fits within two ULPs. VERIFIED — checked against an oracle independent of the computation: a closed form, a finite difference, a conservation law, the true vector field. SELF-CONSISTENT — computed two ways by the same engine from the same parsed tree and shown to agree. Strong evidence that the implementation is coherent; no evidence that the model is right. EXACT, UNCHECKED — symbolic and correct by construction (differentiation), with no check run because none is thought necessary. HEURISTIC — a search or a rewrite with no normal form, no completeness claim, and no verdict.

3 · Parser

All class methods on ExpressionParser; entry is parse(input) = tokenize → infix_to_prefix → build_tree.

  • Tokenize. pi/e are textually replaced with Math::PI/Math::E before scanning; numbers become Float. Precedence map OPERATORS: + - = 1, * / = 2, ^ = 3, functions = 4.
  • Normalize. insert_unary_minus rewrites a leading/post-operator - into the pair -1.0, * (the raw form caused a SystemStackError) — except after ^, where the negated operand is parenthesised instead (see the card below). insert_implicit_multiplication inserts * between operand-enders and operand-starters (2x, 2(x+1), 2sin(x), (x+1)(x-2)).
  • Reverse shunting-yard. The token list is reversed, parens swapped, run through a modified shunting-yard to postfix, then reversed to prefix. Functions are pushed and popped immediately after their ).
The associativity fix. Because the list is reversed, should_pop_for_postfix? uses flipped comparisons: left-associative operators pop on strict stack_prec > current_prec, while the right-associative ^ pops on stack_prec ≥ current_prec. The pre-fix code had these inverted, so 5-2+1, 8/2/2, and 2^3^2 evaluated wrongly. Guarded by test_associativity.rb (17 cases).
A silent wrong answer, and why x^-1 hid it. The (-1) * rewrite is sound only where the minus sits at a precedence below multiplication. ^ binds tighter than *, so in an exponent the multiplication escaped: x^-3 became (x^-1) * 3, a different function — 1.5 at x=2 instead of 0.125. Nothing errored; the answer was simply wrong. x^-1 is the form that appears most often, and it is the one case the bug cannot touch (multiplying by 1 changes nothing), so the engine looked healthy while x^-2, x^-3 and x^-0.5 were all quietly incorrect.

It also poisoned composition. to_infix prints that form — d²/dx²(1/x) renders as 2 * (x ^ -3) — so every module that builds expressions by re-parsing printed infix (vector_field_ops, general_relativity) got back a different function than it put in. That is how it surfaced: a divergence card showed two correct partials, 2·x⁻³ and 0, and then reported their sum as 6·x⁻&sup9;¹. Now the exponent keeps its own parentheses. Guarded by probe_parser_exponent.rb (29 checks, scored against Ruby’s own float arithmetic rather than against the engine).
The scanner dropped what it could not read. tokenize splits with String#scan, which silently skips any character its pattern misses — and the pattern never matched × or ÷, the very glyphs to_readable_string prints. So 6 ÷ 2 lost the operator and parsed as the implicit product 6 × 2 = 12, and 2 × -3 lost it and parsed as the subtraction 2 - 3 = -1. Copying a displayed answer back into the input bar quietly changed the function. Display glyphs (× · ÷ − and friends) are now folded to their ASCII operators before scanning, and a character the scanner still cannot classify raises instead of vanishing — a typo should be an error, not a different question.

Constants are not symbolic: pi/e are float literals at lex time and every number is a Float. This one decision shapes — and bounds — everything downstream (§20, §22).

4 · AST & evaluation

ExpressionNode fields: isleaf, data (operator/function/variable string, or Numeric), left, right, parent, type. Unary functions hang their argument on right. connect(child, "L"|"R") wires children + back-pointer; deep_clone copies the subtree.

evaluate(var_values) is the numeric oracle the whole verification philosophy rests on. Recursion: number leaves → to_f; variable leaves → var_values[data] (missing → 0.0); operators dispatch via a large case:

  • Arithmetic + - * / ^ (division by zero → Float::INFINITY).
  • Standard functions map to Ruby Math; reciprocal trig is computed as 1/tan, 1/cos, 1/sin with zero-guards; ln/sqrt return NaN out of domain; arcsin/arccos require |arg| ≤ 1.
  • Special functions Si, Ci, Ei, li, FresnelS, FresnelC are evaluated by composite Simpson quadrature (sf_quad, n = 600) over their defining integral; Ci/Ei/li add the SF_EULER_GAMMA + ln(…) offset. erf uses Math.erf. (All match published tables to ~1e-10.)

to_readable_string/to_latex (in tree_visualizer.rb) render the three output forms; to_latex emits special functions as \operatorname{…} so li(x) is not mistaken for a variable product.

5 · Differentiation (rule order)

Exact and total — there is no "can't differentiate." compute_derivative(node, variable, steps, aggressive_simplify) is one case node.data evaluated top to bottom; subtrees are reused via deep_clone to avoid aliasing. With track_steps, each rule appends {rule, from, to}.

  1. Leaf base cases: x → 1, constant → 0.
  2. + sum, - difference.
  3. * product u'v + uv'; / quotient (u'v − uv')/v².
  4. ^ three branches in order: (a) power rule xⁿ → n·xⁿ⁻¹ (base = var, const exponent); (b) generalized power + chain fⁿ → n·fⁿ⁻¹·f' (const exponent); (c) general f^g via logarithmic differentiation f^g·(g'·ln f + g·f'/f).
  5. Trig (chain ·u'): sin cos tan cot sec csc; hyperbolic sinh cosh tanh sech csch coth; inverse hyperbolic arcsinh arccosh arctanh.
  6. ln, exp; inverse trig arctan arcsin arccos; sqrt → 1/(2√u)·u'.
  7. Special functions (one shared branch): erf' = (2/√π)e^(−u²), Si' = sin u/u, Ci' = cos u/u, Ei' = e^u/u, li' = 1/ln u, FresnelS' = sin(u²), FresnelC' = cos(u²) — each ·u'.
  8. abs → (u/|u|)·u'. Fallback: unknown operator → 0.

6 · The integration routine — exact order

This is the heart of the engine. integrate(variable) dispatches on @use_experimental_integration: when true it runs the cascade (integrate_experimental → risch_integrate); otherwise it calls the standard integrator compute_integral directly (§7). Both results pass through finalize_integration.

Depth / budget guard. risch_integrate wraps risch_integrate_inner with RISCH_MAX_DEPTH = 30 and RISCH_MAX_CALLS = 4000. On exceed it returns an integral(…) marker instead of recursing — the anti-hang stop (e.g. sin(x)/x returns a marker in ~0.04 s).

risch_integrate_inner runs these phases in this order; each is gated by a respond_to? capability check plus a structural predicate, and the first to yield a marker-free result returns immediately. Phases marked (rewrite) mutate the working node and fall through; phases marked (recurse) transform and re-enter risch_integrate.

  1. Division u-sub on the raw form. if node.data == '/' and not a rational function — attempt_u_sub_division. Catches ln(x)/x, sin(ln x)/x before normalization rewrites a/b → a·b⁻¹.
  2. Special-function forms. on the raw shape — special_function_integral → erf, Si, Ci, Ei, li, Fresnel (§9).
  3. Normalize (rewrite) — normalize_expression (§10), then algebraic_simplify.
  4. Table lookup. table_lookup_integral — the fastest closed-form path (§8).
  5. General u-substitution. if node.data == '*' — attempt_general_u_sub; logs the candidate list. Runs before trig identities.
  6. Special product families. if node.data == '*' — attempt_special_product: poly·exp·trig, mixed odd trig powers, poly·trig² (§9).
  7. Trig identity rewrite (rewrite) — apply_trig_identities (§8).
  8. Distribute product over sum (recurse). if * over +/- — expand and re-integrate.
  9. Product-to-sum trig (recurse) — apply_product_to_sum (sin·cos, sin·sin, cos·cos).
  10. Inverse trig / lnⁿ. if is_inverse_trig? — integrate_inverse_trig (with an ln^n reduction).
  11. Rational function. if is_rational_function? — attempt_rational_integration → partial fractions (§8). Highest-priority "type" phase.
  12. Trig power reduction. if is_trig_power? (sin/cos/…ⁿ, n>1) — attempt_trig_power_reduction.
  13. Quadratic radical / trig sub. if has_quadratic_radical? — attempt_radical_integration.
  14. Smart substitution. if can_apply_smart_substitution? — attempt_smart_substitution. Deliberately before by-parts.
  15. Integration by parts. if can_apply_integration_by_parts? — attempt_integration_by_parts: LIATE choice, special-cases exp×trig, computes du, recursively gets v and ∫v du via risch_integrate.
  16. Fallback. compute_integral — the standard integrator (§7); returns a marker if it too cannot solve.
Honest-marker finalize. finalize_integration runs once on the top-level result: if the tree still contains an integral marker but is not itself a lone marker, it collapses the whole tree to one marker over the original integrand. This stops a later simplify pass from cancelling a partial marker and presenting a clean-but-wrong antiderivative (the historical x²·eˣ·sin x bug). Combined with §11, this is why the engine never reports a confidently-wrong integral.
The Fundamental Theorem needs a continuity check, and did not have one. F(b) − F(a) was evaluated straight across a pole. ∫₋₁¹ dx/x² is divergent and came back as −2 — a negative area under a strictly positive integrand, so not merely inaccurate but impossible. ∫₋₁¹ dx/x came back as 0 with no mention that this is a principal value, and ∫₋∞∞ dx/(x³+1) came back as 1.79 from Simpson, which skips non-finite samples and so integrates straight through a singularity.

A continuity check now runs before any of the three routes. Finding a singularity is only half of it, because an interior one does not imply divergence — ∫₋₁¹ dx/√|x| = 4 converges. The guard locates the blow-up by ternary search on |f| (a refined grid fails: its points sit at fixed offsets, so on tan near π/2 it never lands closer than the original scan and a real pole reads as a plateau), then asks the one-sided limits by watching the sliver ∫ over [x₀−εₖ, x₀−εₖ₊₁] as the cutoff shrinks:
convergent slivers collapse 1/√|x| → 0.137, 0.043, 0.014 log slivers hold steady 1/x → ln 10 each time power slivers grow 1/x² → 900, 9 000, 90 000
A side that diverges makes the integral divergent even when the two sides cancel — that is ∫₋₁¹ dx/x, whose halves both diverge and whose symmetric combination is 0. The Cauchy principal value is reported as a labelled extra, never as the answer. Endpoint singularities are deliberately out of scope: ∫₀¹ dx/√x and ∫₀¹ ln x dx are improper only at a bound and both converge, so flagging them would be a false refusal. Guarded by probe_improper.rb (19 checks), and the regression output is byte-identical.

10 · Normalizer, Polynomial & Simplify

normalizer.rb — canonicalization (non-mutating)

normalize_expression deep-clones, normalizes children, then applies a fixed pipeline: fold constants → canonical operand order (constant left) → negation (0−x → −1·x) → identity laws (x+0, x·1, x/x→1, x^0→1, …) → radicals (√x → x^½) → reciprocal powers (f/xⁿ → f·x⁻ⁿ) → combine power products (xᵃ·xᵇ → x^(a+b)) → polynomial term collection (for +/- roots, via Polynomial) → common-factor cancellation (for /, GCD, only on exact division).

Sparse @coeffs = {degree => coefficient} (zero polynomial = empty hash, degree == -1). Provides arithmetic, divmod (long division), Euclidean gcd (monic), derivative/integral, and root finding: rational_roots (rational-root theorem, root test at |eval| < 1e-10), factor_linear_roots (divide out (x−r) with multiplicity), discriminant/quadratic_roots. from_expression returns nil for anything non-polynomial (transcendental, non-integer/negative power, non-constant denominator).

A fixed-point pass rewriter: identity laws, constant folding, like-term collection, sign normalization, repeated until stable. track_steps records each rewrite for the Solution Steps panel and the live "polish" phase.

A rewrite that checks itself. The collectors above are polynomial-shaped — they go through Polynomial.from_expression, which returns nil for anything transcendental — and the two general rules that did fire (x + x = 2x, x − x = 0) demand an exact node match, so any explicit coefficient defeated them. eₓ·cos y + (−1)·eₓ·cos y stayed on screen as a sum whose terms cancel, which is how the Laplacian of a harmonic function came out correct but visibly unfinished.

collect_like_terms_general takes a whole +/− chain at once: it flattens the chain (the right operand of a minus flipping sign), splits each term into a numeric coefficient and a multiset of factors, keys the term on the sorted factor list so a·b and b·a agree, sums the coefficients and rebuilds. ∇²(eₓcos y), ∇²(e²ₓcos 2y) and ∇²(x²−y²) now all print 0.

It refuses to apply itself unless it can show the value is unchanged. Two of the bugs documented above were rewrites that silently altered an expression, and this one is more aggressive than either, so before replacing anything it evaluates the old and new subtrees at several sample points and abandons the rewrite on any disagreement (points where either side is non-finite prove nothing and are skipped, but at least one usable comparison is required). The probe tests the guard in both directions — that a correct collection is accepted and that one with a deliberately wrong coefficient is rejected — because a guard that only ever says yes is not a guard.
A hang, found by fuzzing rather than by guessing. Polynomial#divmod is Euclidean long division: each step is meant to cancel the remainder’s leading term exactly. Polynomial#initialize prunes a coefficient only when it is exactly 0.0, and in floating point that cancellation routinely leaves a residue around 1e−16 instead. The remainder’s degree therefore never dropped, the loop never exited, and Polynomial#gcd — reached from normalizer.rb’s cancel_common_factors — spun forever. Simplifying 12.25 / (y − 2) hung the engine outright; in the browser build that is a frozen tab rather than an error message. Neighbouring inputs like 12 / (y − 2) and 3.5 / (y − 2) were fine, which is why no example-based test ever met it.

divmod now compares the degree before and after each step. A residue that is negligible against the rest of the polynomial is rounding and is discarded so the degree strictly decreases; a residue large enough to be real means the step did not divide as intended, and the loop stops rather than spinning. Termination no longer depends on exact float cancellation.

How it was found matters more than the fix. probe_simplify_fuzz.rb generates random expressions from a fixed seed, simplifies each under a per-expression timeout, and demands that the value at three sample points is unchanged. It currently clears 5 585 expressions in about four seconds with no value change, no exception and no timeout. Three separate value-changing rewrites and this hang had all survived the example-based suites; a property that must hold for every expression finds the next one without anyone having to guess where it will be.

11 · Verification — the honesty layer

After integration, verify_integral(integrand, result, variable, n_points: 15) checks the result against independent numerics, never against the engine's own reasoning:

for 15 sample points x: F'(x) ≈ (F(x+h) − F(x−h)) / 2h must match the integrand f(x) accept a point if relative error < 1% · accept the result if ≥ 90% of points pass

Tolerance was tightened 5%→1% and threshold 80%→90% after the looser bounds accepted ~3%-wrong answers. The same dF/dx==f principle verifies special-function results; an analogous "compute it two ways and compare" verifies every field theorem and transport identity (§14). Principle: a proof the engine generates is trusted only once an oracle it did not write agrees.

A check whose outcome nobody sees is not a check. This verification has run on every experimental integration since it was written, and its verdict went nowhere. integrate_experimental snapshotted the debug log one line before the verify block appended its entry, so [Verify] Verified at 15/15 points never reached the result object. The only way to see it was to switch on Strategy View, which reaches the same conclusion by a different route through integration_tracer.rb. The engine was marking its own homework and then filing the mark in a bin.

The snapshot now happens after verification, and the verdict is carried as a first-class field rather than a log line, so both transports hand it to the client and it appears as a badge beside the antiderivative. The absence of a badge is meaningful too: when the result still holds an unevaluated integral marker there is nothing to differentiate, so no check is attempted and none is claimed. Guarded by probe_integrate_verdict.rb (14 checks), which asserts both the presence of the verdict on solved integrals and its absence on x^x.

12 · Series — Taylor / Laurent / Padé

Taylor: coefficients f⁽ⁿ⁾(c)/n! from successive symbolic derivatives at the center, rendered as exact rationals when one matches to 1e-9. Laurent EXPERIMENTAL: a pole of order m is detected numerically, the principal part recovered by symbolically simplifying (x−c)ᵐ·f so the pole cancels exactly (evaluating the uncancelled form near a pole is catastrophically ill-conditioned); unstable coefficients truncate the series honestly. Inaccuracy bounded by the Lagrange remainder |R| ≤ M·|x−c|ⁿ⁺¹/(n+1)!, M sampled on [c−½, c+½]. (The old taylor_series.rb is demo scaffolding; the real engine is series_expansion.rb.)

Padé approximants (pade.rb)

A Taylor polynomial is blind to poles — it diverges outside the circle through the nearest singularity. The [L/M] Padé approximant P(u)/Q(u) matches the Taylor series through order L+M but its denominator puts the poles back: the M×M Toeplitz system Σ c_{k−j} q_j = −c_k (Gaussian elimination, partial pivoting) fixes Q, and the numerator follows by convolution. [3/3] of tan x is (x − x³/15)/(1 − 2x²/5) with a Q-root at √(5/2) = 1.5811 — within 0.7% of π/2 — and keeps tracking far beyond the Taylor radius (ln(1+x) at x=3: Padé 1.3636 vs truth 1.3863, while Taylor-4 gives −12.75). For rational f the table closes: the approximant is exact and reported as such.

Spurious poles, flagged. Finite Padé tables can produce Froissart doublets — poles of Q where f is perfectly finite. Every real Q-root is therefore tested against f itself (does |f| actually blow up in a neighbourhood scaled to the pole-location error?); artifacts are labelled SPURIOUS in the UI rather than hidden. Verification: defining-relation residuals + numeric agreement with f near the center and across the window. 34/34 probe cases (amplitude-invariant pole tests and distant-pole root-finding hardened by an adversarial review pass). Fixing the Taylor-coefficient pipeline also uncovered and fixed a derivative-core bug: repeated differentiation accumulated ((n−1)−1)… exponent subtrees until 0·x⁻¹ = 0·∞ = NaN; exponents are now folded at derivative time (§5).

13 · Residue theorem

Why not every definite integral? The residue theorem computes contour integrals. To use it on a real integral you must embed that integral in a closed loop whose remaining part you can evaluate. ∫₀¹ x² dx admits no such loop — [0,1] is not a cycle and nothing closes it — so this is a structural limit, not a missing feature. Two shapes do close: an infinite interval (a semicircle at infinity, whose contribution vanishes when deg Q ≥ deg P + 2) and a full period [0, 2π], which closes into the unit circle. The remaining classical families — Fourier-type via Jordan's lemma, and keyhole contours for branch cuts — are not implemented.

Type 1 — improper rational integrals

Improper integrals of rational P/Q with deg Q ≥ deg P + 2 over (−∞,∞) (and even integrands over (0,∞)) by contour integration: ∫ = 2πi · Σ Res (upper half-plane). Procedure: extract Polynomials → find roots (quadratic formula → rational-root factoring → Durand-Kerner for any remaining degree ≥ 3) → real-axis guard → select upper-half poles → compute residues → sum → 2πi·Σ.

Three correctness fixes (found by a 16-case headless battery before de-experimentalizing):
  • Real-axis poles: a pole on the contour means the integral diverges / is principal-value only. The guard now declines if any pole is on the real axis (it previously declined only when all were, so 1/(x³+1) returned a bogus finite number).
  • Repeated poles: simple poles use Res = P(z₀)/Q'(z₀); order-m poles use (1/2πi)∮f dz on a small circle (trapezoid is spectrally accurate). The radius was a tiny 1e-5 that bled precision (1/(x²+1)² was 0.5% off); it now adapts to 0.3 × the nearest other pole — exact.
  • Sextics+: root dispatch only routed degree 2 and 4 to the numerical finder; all degree ≥ 3 now go to Durand-Kerner, so 1/(x⁶+1), 1/(x⁸+1) work.
16/16 closed forms exact, 4/4 inapplicable cases declined.

Type 2 — trigonometric integrals over a full period NEW

A finite interval that works, because it closes. Substituting z = e^{iθ} walks the unit circle exactly once, turning a rational function of sin and cos into a rational function of z:

cos θ = (z + 1/z)/2 sin θ = (z − 1/z)/(2i) dθ = dz/(iz) ∫₀^2π R(cos θ, sin θ) dθ = ∮|z|=1 R(…) · dz/(iz) = 2πi · Σ Res inside |z| < 1

The integrand is converted to a numerator/denominator pair of complex polynomials by walking the AST (polynomial.rb is real-only, so this uses a small local complex-coefficient helper), roots come from a complex Durand-Kerner, and residues use N/Q′ for simple poles or a small numerical contour for higher order — 1/(2+cos θ)² exercises the double-pole path. Verified examples: ∫₀^2π dθ/(a + cos θ) = 2π/√(a²−1), ∫₀^2π dθ/(5 − 4cos θ) = 2π/3, ∫₀^2π dθ/(1 + sin²θ) = π√2, ∫₀^2π cos⁴θ dθ = 3π/4.

Refusals and the oracle. A pole on the unit circle means the integral diverges or is principal-value only — 1/(1 + cos θ) is declined, mirroring the real-axis guard of Type 1. Integrands that are not rational in sin/cos (exp(cos θ), a bare θ, or cos(2θ) whose argument is not the bare variable) are refused rather than approximated. Every accepted result is then checked against periodic trapezoid quadrature, which converges exponentially for smooth periodic integrands and so is an unusually sharp oracle; a disagreement above 1e−6 relative causes the contour result to be withdrawn. 23/23 probe cases.
A bug this feature exposed. Both transports parsed integration bounds with String#to_f, so "2*pi" silently became 2.0 and "pi" became 0.0 — the engine integrated over the wrong interval and reported the answer as if it were the requested one. Harmless-looking until [0, 2π] became a meaningful interval. Bounds now go through the engine's own parser (which substitutes π at lex time), so 2*pi, pi/2 and 2*pi/3 all work; ∫₀^π sin x now returns 2 rather than 0.

Dimension is a slider, and it gates the menu. Curl is the sole exception, and for a structural reason rather than an implementation limit. The curl is the antisymmetric part of the derivative, which has n(n−1)/2 independent components:

Only at n = 3 does the component count coincide with the dimension, which is the entire reason the cross product and the curl exist in their familiar form. So the dialog offers curl at n = 2 and n = 3 and disables it everywhere else, naming the count it would have had; if the dimension changes out from under a selected curl, the menu falls back rather than computing something that is not one. What it refuses, and why. Each of these would otherwise produce a confident wrong number. An axis named pi, e, or any function name is refused: the parser substitutes those textually before a variable lookup can happen (§3), so ∂/∂e would come back as 0 and the echoed input would read 2.718^2. A repeated axis name is refused: two slots called x are not two dimensions, and ∇·F over [x, x] would add ∂F/∂x to itself and report twice the true divergence. A vector mode with a missing or mis-counted component is refused rather than padded. And the dialog caps at six axes — stated up front, never silently truncated.

17 · Equation discovery — SINDy

Every other operation here runs forwards: given an expression, produce a derivative, an integral, a series. sindy.rb runs the engine backwards — given only a trajectory, recover the differential equation that produced it. The method is Sparse Identification of Nonlinear Dynamics (Brunton, Proctor & Kutz, PNAS 2016).

Ẋ = Θ(X) · Ξ Θ = library of candidate terms · Ξ = coefficients, forced SPARSE

Θ(X) holds every candidate evaluated along the trajectory — monomials up to a chosen total degree, optionally sin/cos of each variable. Ξ is found by STLSQ: solve the least-squares problem, zero every coefficient below λ, re-solve on the survivors, repeat to convergence. Sparsity is the prior that turns a mere fit into a candidate physical law — a dense Ξ would interpolate the data equally well and mean nothing.

Pipeline

  • Truth is the engine's own. Each preset system is a set of ordinary expression strings parsed by MathematicalExpression, integrated with RK4. A user-supplied ODE therefore works exactly like a preset — you can type any autonomous system and watch it get rediscovered.
  • Derivatives. The estimate of Ẋ is the accuracy bottleneck. On clean data the 4th-order 5-point stencil (O(dt⁴)) is used, which is what lets coefficients come back at full precision; with noise the code switches to a Savitzky-Golay window (quadratic fit, widened with the noise level), which smooths and differentiates in one pass.
  • Regression. Normal equations with a scale-relative ridge (1e-12·max diagonal) and Gaussian elimination with partial pivoting.

Verification — and a chaos caveat

The discovered model is judged only by oracles the regression never saw:

  1. Vector-field agreement — ‖f_disc(X) − f_true(X)‖ / ‖f_true(X)‖ at every sampled state. This carries the verdict.
  2. Re-simulation — RK4-integrate the discovered model from the same initial condition and compare trajectories.
Why the trajectory check cannot carry the verdict. For a chaotic system (Lorenz) two nearby trajectories separate exponentially even when the model is exactly right. Scoring long-horizon trajectory error would therefore condemn a perfect model. So the re-simulation is scored over roughly one Lyapunov time and reported as corroboration only, with the divergence labelled as genuine physics rather than model error. Reporting it any other way would be precisely the sort of confidently-wrong result the rest of the engine refuses to emit.

18 · Conditional interval bounds

evaluate_interval walks the same expression tree as ordinary evaluation, carrying [lo, hi] through each operation. Basic floating-point operations widen outward using adjacent representable values. Library transcendental results widen by two ULPs. That last step assumes a bound on the platform math library’s error; it is not independently certified for every input or platform. The UI therefore calls these conditional interval bounds. Exact rational and algebraic checks are a separate capability.

  • Range enclosure. Repeated variables introduce dependency overestimation: x − x on [0,1] gives [−1,1] when the two occurrences are treated independently. Subdivision narrows that excess. Division by an interval containing zero returns an unbounded interval.
  • Global-minimum bounds. A 1D/2D branch-and-bound search discards a box when its interval lower bound exceeds the best available upper bound. Surviving boxes may contain a minimizer; they are not each a proven unique root. Narrow dips can survive even when point samples miss them. A finite search budget can leave a wide gap.
  • Integral brackets. Adaptive Darboux-style sums accumulate segment width times a function enclosure. They give a conditional bracket rather than just a point estimate. The independent Simpson estimate is a regression check, not a proof of the library assumption.
What is checked. Dense samples test range containment and global-minimum lower bounds; integral probes compare against known results and independent quadrature. These checks catch implementation errors. They do not establish a uniform bound on every transcendental-library call. Unsupported functions, unbound variables and invalid domains are refused; unbounded answers remain visibly uninformative.
Try the dependency example. For x² − x on [0,1], the one-box interval is about [−1,1]. Thirty-two subdivisions narrow it to about [−0.28125,0.03125], containing the true range [−0.25,0]. Then try the narrow Gaussian dip: compare the plotted samples with the region retained by interval subdivision. Wide bounds and unsupported cases are useful diagnostics, too.

20 · Exact arithmetic (ℚ, ℚ(α)) — the gate

Sections 18 and 19 pushed on verification. This one pushes on the constraint underneath everything: the float-only numeric core (§3). exact_arithmetic.rb adds a third evaluator beside the two we had, on the same AST. They are not competing implementations — they answer three different questions, and the UI colour-codes them from data the engine itself tags:

EvaluatorColourAnswersCost
evaluate (float)amberalways, never refusessilently approximate: 0.1+0.2 → 0.30000000000000004
evaluate_interval (interval bounds, §18)greenconditional enclosure, or refusala range, not a number: [0.3, 0.3000000000000001]
evaluate_exact (ℚ) NEWpurpleexactly, or refusesonly rational answers exist: 0.1+0.2 → 3/10

The refusal is the feature. sqrt(2), sin(1), exp(1), ln(5) return no value and say why, rather than degrading to a float. sin(0), cos(0), ln(1), sqrt(9/4) come back exactly. Recovering a rational from a parsed float distinguishes two genuinely different cases and reports which: exact (2.0 is 2; binary fractions are exact) versus recovered (0.1 is not 1/10 — it is 3602879701896397/36028797018963968 — but 1/10 is the only simple rational whose double this is). A double with no small-denominator reading is refused rather than silently rationalised, and a runaway numerator hits a bit-length budget and refuses instead of hanging.

Why the zero-test is the whole point

"Is this coefficient zero?" is a guess at 1e−10 tolerance in float and a fact in ℚ. Every decision procedure — Risch, Rothstein–Trager, Gosper — is assembled out of exact zero-tests, which is precisely why none of them could be built on the existing core (§22). ExactPolynomial is the parallel to polynomial.rb, which cannot be retrofitted: its constructor runs coeff.to_f on every coefficient, so a Rational cannot survive being stored, and its GCD normalises by float division.

A measured failure, not a hypothetical one. Take f = (x − 1/3)⁴ and ask for gcd(f, f′). The true answer is (3x − 1)³, degree 3. The exact path returns exactly that. The float path returns degree 0 — "no common factor at all." That is not a rounding discrepancy but a structurally wrong answer: 1/3 is not a representable double, so a remainder that should be exactly zero never lands on 0.0, and the Euclidean algorithm runs on to a nonzero constant. (x − 1/7)³ fails the same way (exact degree 2, float degree 0). This is the operation Rothstein–Trager is built on.

What this unlocks

  • Exact GCD via the primitive PRS — intermediate coefficients stay bounded instead of exploding as naive rational Euclid does, and the result is canonical primitive (integer coefficients, positive leading term) rather than merely monic.
  • Squarefree decomposition (Yun) — splits f by root multiplicity; Rothstein–Trager runs on the squarefree part, so this is a hard prerequisite. Requires characteristic 0 and an exact GCD.
  • Resultants via the Euclidean PRS with the standard sign/leading-coefficient bookkeeping. Res(f, f′) = 0 exactly when f has a repeated root — an exact test where the float path could only compare against a tolerance.
  • Exact rational roots — rational-root theorem with exact verification, so "x² − 2 has no rational roots" is proven rather than measured.

ℚ(α) — algebraic extensions NEW

The step above made a point of refusing sqrt(2), because √2 is not rational and inventing a rational for it would be a lie. algebraic_field.rb is the field where it no longer has to. An element of ℚ(α) is a polynomial in α of degree < deg(m) with rational coefficients, reduced modulo the minimal polynomial. So √2 is not stored as 1.4142135623730951 (which squares to 2.0000000000000004) — it is stored as the symbol α together with the rule α² = 2, and squaring it gives exactly 2.

  • Inverses come from the extended Euclid added to ExactPolynomial: solve u·p + v·m = 1, then p⁻¹ ≡ u (mod m). This is the step that makes ℚ[x]/(m) a field rather than a ring, and it is only possible exactly — a float Euclid never terminates cleanly. (1+√2)⁻¹ = √2−1, φ⁻¹ = φ−1, (∛2)⁻¹ = (∛2)²/2, all exact.
  • Norm and trace are computed two independent ways — the resultant of m with the element, and the determinant/trace of the multiplication matrix in the basis 1, α, …, αn−1 — and the two must agree. A built-in oracle rather than a claim.
  • The numeric embedding is decorative. α's float value is used only for display and as an independent cross-check; it is never fed back into the exact arithmetic. ℚ(i) has no real embedding at all and works perfectly.
What "irreducible" is allowed to claim. ℚ[x]/(m) is a field only when m is irreducible, and proving irreducibility over ℚ in general is real work. The module states exactly what it checked: squarefree (exact) and no rational roots (exact) — which for degree ≤ 3 is a proof, and for degree ≥ 4 is not (m could split into two quadratics). Degree-4+ fields are therefore labelled ASSUMED, not proven. And if an inverse later fails because gcd(p, m) has positive degree, that failure is reported as what it actually is: a proof that m factors. Probed with (a²+1)(a²+2), which passes both cheap checks and is then caught by the inverse.

Scope: strictly additive and switchable — a mode on the existing ℚ tool, not a new one. No existing operation is routed through the exact path, the float default is untouched, and "float only" reproduces precisely what the engine did before any of this existed. 44/44 + 40/40 probe cases. What is still not here: polynomials over ℚ(α) (the immediate next step — RT's gcd(f − c·g′, g) has coefficients in this field), factorisation over ℚ, and the differential-field tower.

What you should see. Three lanes, and the interesting one is the lane that says nothing.

Run 0.1 + 0.2 − 0.3 in compare mode. This is the zero-test in its sharpest form, and the three lanes take three genuinely different epistemic positions on the same question. Float answers 5.551115123125783e−17 — it says the expression is not zero, and it is wrong. The interval evaluator answers [−5e−324, 1.1102230246251568e−16] — an interval straddling zero, which is the honest statement that double precision cannot decide this. Exact answers 0. Not "approximately zero": zero. Plain 0.1 + 0.2 shows the same shape — float 0.30000000000000004, exact 3/10, delta 5.55e−17.

Then run the polynomial lab on f = (3x−1)⁴/81. Ask for gcd(f, f′). The exact lane returns 27x³ − 27x² + 9x − 1, degree 3. The float lane returns 1, degree 0 — "these polynomials share no factor". That is not a rounding error, it is a structurally wrong answer to a yes/no question, and it is why every decision procedure downstream of this (Risch, Rothstein–Trager) needs exact arithmetic rather than a tolerance. Yun's squarefree decomposition alongside it reports (3x−1) with multiplicity 4, and Res(f, f′) = 0 exactly.

What honest failure looks like. Ask for sqrt(2). The exact lane returns no value, its colour drops to grey, and it says: "sqrt(2/1) is irrational. Refusing beats inventing a rational that is not there." The refusal is the product. In ℚ(α) the same √2 becomes representable — α with the rule α² = 2, where squaring gives exactly 2 rather than 2.0000000000000004, the inverse comes from the extended Euclid as ½α with a product of exactly 1, and the norm is computed two independent ways that must agree. Note what the field report claims and what it does not: for α² − 2 it says PROVEN irreducible — squarefree with no rational roots, and for degree 2 that is sufficient. Above degree 3 irreducibility is assumed, and the report says assumed.

22 · Limits & the Risch question

Is the integrator "Risch"? No.

Despite the filename experimental_risch.rb, integration is the deterministic heuristic cascade of §6 — a fixed strategy order. The true Risch algorithm is a decision procedure: it returns an elementary antiderivative or proves none exists (Liouville's theorem). That needs a differential-field tower, Hermite reduction, Rothstein–Trager (resultants), and the Risch differential equation — none present. The only probabilistic component here is the verifier.

Do we still need it? — out of scope now, the natural successor later

  • It presupposes exact arithmetic. Risch lives on exact zero-tests, GCDs, resultants, factorization over ℚ and algebraic extensions. On a float-only core (sin(pi) ≈ 1.2e−16) those tests are meaningless — so Risch is gated on the exact-rational/algebraic-number rewrite (the same one motivating a C++/WASM-native port).
  • It needs a different data model: canonical sparse polynomials over a field tower, not a representation-dependent expression tree.
  • But it's the one capability heuristics fundamentally can't give: the decision. Today a marker means "ran out of patterns," not "proven non-elementary."
Recommended sequencing. (1) exact arithmetic (rationals → algebraic numbers); (2) canonical polynomial / rational-function representation + a differential-field tower; (3) the transcendental Risch (Hermite + Rothstein–Trager + Risch DE) — the tractable ~80%. Skip full algebraic Risch (research-grade). High-value middle ground needing only step 1: Rothstein–Trager for the rational-function logarithmic part, which alone conquers 1/(x⁴+1) and the general P/Q log cases — today's biggest coverage gap.

Status: step 1 is now essentially done (§20). Exact rationals, exact polynomial GCD, squarefree decomposition, resultants, extended Euclid, and algebraic extensions ℚ(α) all exist and are probe-verified — that is the toolkit Rothstein–Trager consumes, including the field its constants live in. What remains before RT is a build rather than a research project: polynomials with coefficients in ℚ(α) (so gcd(f − c·g′, g) can be computed where c is algebraic), and factorisation over ℚ for the general case. Step 2's differential-field tower is untouched. The gate is open; RT itself is not implemented and is not claimed to be.

Other known limits

  • Float-only numeric core — no exact rationals or symbolic constants (the deepest constraint).
  • 1/(x⁴+1) — elementary but unsolved; needs irrational quadratic factoring.
  • Matrix exponentials (A^x, e^(At)) — need a matrix value type + non-commutative products; assessed HARD, not shipped.
  • Pattern fragility — heuristic matching is representation-dependent; normalization mitigates but doesn't eliminate it.

23 · Where this sits — an honest comparison

Every section above says what the engine does. This one says how that compares to the tools a professional would actually reach for, area by area, without flattering the project. The reference points are Mathematica and Maple (commercial), SymPy and SageMath/PARI (open source), Arb and INTLAB (rigorous numerics), xAct and SageManifolds (differential geometry), and PySINDy (equation discovery).

The core method faithfully: candidate library, sequential thresholded least squares, verification against the true vector field (§17). The most current thing here. The algorithm is genuinely modern research and the implementation is honest — including reporting FAILED when the truth lies outside the library's span. It has none of the later variants, and the library is small.
What is actually distinctive. Not any single algorithm — every one above exists in a more capable form somewhere. Two habits are the unusual part.

First, the refusal discipline. Mainstream systems will hand you a wrong-branch antiderivative or a coefficient that is zero only to within a tolerance, with no indication that anything is uncertain. This engine is built so that the failure mode is a marker rather than a confident wrong answer: unsolved integrals come back as markers, residues decline when a pole sits on the contour, the exact evaluator returns nothing rather than a float, curl refuses in 4D rather than inventing a vector, and a variable named e is rejected rather than silently read as 2.718. That is a design stance, not an algorithmic achievement — but it is the stance that makes a small engine trustworthy.

The stance has to be enforced, not assumed. Fact-checking the paragraph above found a place where it was simply false. The definite-integral path did not check for a singularity inside the interval, so it applied the Fundamental Theorem straight across a pole: ∫₋₁¹ dx/x² is divergent and the engine reported −2 — a negative area under a strictly positive integrand, which no correct answer could be. ∫₋₁¹ dx/x reported 0 without calling it a principal value, and ∫₋∞∞ dx/(x³+1) reported 1.79 by Simpson after the residue route had correctly declined the very same integral. A continuity check now runs first (§6), and all three refuse. The lesson is the one this whole document keeps arriving at: a doctrine is only as good as the check that enforces it, and the claim was worth less than the ten minutes spent testing it.

Second, the testing method. Results are scored against oracles independent of the computation that produced them — closed forms, finite differences, conservation laws, a nonzero curvature invariant — never against the engine's own reasoning. And two techniques have repeatedly found what example-based tests missed: a property fuzz asserting that simplification never changes a value (§21), which found a non-terminating polynomial division on its first wide run, and diffing the whole regression output against a pristine worktree of HEAD, which is how seven silently mis-printed antiderivatives were caught — they had been passing their numeric checks for months because the checks read the tree while the bug was in the printer.

The fair summary: as a computer algebra system this is a competent, unusually well-verified undergraduate-to-graduate scale engine, decisively behind the established tools in coverage and depth, and behind them structurally in integration until exact arithmetic replaces the float core. As a demonstration of how to know whether a symbolic result is right, it is doing something the big systems largely do not.
